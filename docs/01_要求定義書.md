## 1. 企画概要

### 1.1 サービスのビジョン

個人開発者が、自分が複数案件に対して指示したAIエージェントの**稼働状況・作業内容・成果物・承認待ち**を1か所で把握できる、クラウド型のAIワークスペースを提供する。3Dの仮想オフィスを中心にしつつ、実務向けのタスク一覧、実行ログ、成果物一覧も備える。

GitHub Issue作成などの外部イベントを契機に、事前許可されたワークフローを**追加の手動指示なしで**起動できる。AIはタスクを計画・分担し、コード修正、検証、Draft PR、資料、メッセージ下書きを作る。外部送信や重要変更は人間が最終判断する。

### 1.2 解決する課題

| ID | 課題 | 期待する改善 |
|---|---|---|
| P-01 | 複数案件・複数AIに指示すると進捗を追いにくい | 個人ワークスペースで横断可視化 |
| P-02 | AIが何をしているか、どこで止まったか分からない | 状態・担当・ツール履歴・失敗理由を表示 |
| P-03 | Issue作成のたびに手動でAIへ指示する必要がある | オプトインのイベント駆動起動 |
| P-04 | 実装、テスト、資料化、連絡が分断される | 役割を分けたAIが協働 |
| P-05 | 人間の承認待ちが埋もれる | 承認キュー・通知・差し戻し |
| P-06 | 複数利用者が使う際の情報漏えいが懸念 | 利用者単位でのデータ・権限分離 |
| P-07 | AI利用額・実行時間・失敗率が分からない | Run単位の可観測性と上限設定 |

### 1.3 製品コンセプト

- **Personal-first**：1ユーザーが1つ以上の個人ワークスペースと複数Projectを持つ。初期版は個人利用が原則。
- **Cloud-hosted**：Reactのブラウザ画面を提供し、Hono APIとAWSの実行基盤で運用する。各利用者がローカルサーバーを立ち上げる必要はない。
- **3D + 実務UI**：React Three Fiber/Three.jsで3Dオフィスを描画。タスク一覧・承認・ログは2Dの操作画面から確実に実行できる。
- **Managed executions first**：本サービスが起動・管理したAIの実行だけをMVPで追跡する。別アプリのCodex/Claude Codeの既存ローカルセッションを無断で監視したり、自動的に収集したりしない。
- **Human-controlled**：PRを勝手にmainへマージしない。外部送信・破壊的操作は承認を要する。
- **Original implementation**：Agents Officeの発想・一般的な設計パターンは参考にするが、ソースコード、3Dモデル、固有デザイン、アセット、名称を流用しない。

## 2. 対象利用者・責務

| 役割 | 初期の利用シナリオ | 可視範囲 |
|---|---|---|
| 個人開発者（Owner） | GitHub連携、案件登録、AI起動、タスク監視、承認 | 自分のワークスペースのみ |
| サービス運用者 | 障害対応、システム監視、料金・利用制限 | 原則集計情報。業務データ閲覧は例外的・監査付き |
| 外部サービス | GitHub、LLM、将来のSlack/Driveなど | 接続権限が付与された必要最小範囲 |
| チームメンバー（将来） | 明示的な招待で案件共有 | P2。初期版には含めない |

### 2.1 プライバシー原則

ログインした利用者は、**他の利用者のAI、Issue、タスク本文、コード、承認、ログ、利用額、ドキュメントを閲覧できない**。同じAWS基盤を共有しても、論理的なユーザー境界とジョブ実行の分離を強制する。

## 3. 提供する価値・ユーザー体験

### 3.1 ホーム／3Dオフィス

- 利用者専用のオフィスに、Planner / Developer / Tester / Reviewer等のキャラクターを配置する。
- キャラクターの`idle`、`working`、`waiting_approval`、`failed`等をサーバー側の状態から表示する。
- カードを選択すると「担当Project・タスク・直近のイベント・PR/成果物」を確認できる。
- 3Dの利用が難しい環境では2D一覧で同じ情報へアクセスできる。3D表示は判断の唯一の手段にしない。
- MVPは3〜4体で始め、UI上の表示数と実際の同時実行数は独立した概念とする。

### 3.2 複数案件の可視化

Project A、B、CごとにGitHubリポジトリ、実行ルール、AI権限、成果物を分ける。横断ホームでは自分の案件だけを一覧でき、案件ごとのフィルター・タスク履歴・承認待ちを追える。

### 3.3 GitHub Issue起点の自動開発

利用者がリポジトリと自動実行ルールを**明示的にON**にすると、条件に合うGitHub Issueの作成・ラベル付け等を契機に、AIが計画→実装→テスト→Draft PR作成まで進める。要件不明・危険・予算超過の場合は停止して利用者に判断を求める。

### 3.4 開発以外の作業

将来、調査・ブレスト、仕様書／議事録／スライド下書き、Slack／メール下書き、定期レポートをサポートする。外部システムへの送信・公開は接続権限と明示承認の下で行う。

## 5. スコープとフェーズ

| 段階 | 対象 | 完了基準 |
|---|---|---|
| Phase 0：UX検証 | オリジナル3Dオフィス、ダミーイベント、2D一覧 | 画面からタスク状態と承認待ちを理解できる |
| Phase 1：MVP | ログイン、個人Workspace、複数Project、GitHub App、手動/自動起動、Agent Runner、Draft PR、レビュー再実行、承認/費用/ログ、実3D反映 | テスト用リポジトリでIssue→PR→レビュー差し戻しまで再現 |
| Phase 2：業務拡張 | ブレスト、資料生成、Drive/Slack/Gmail、ナレッジ検索、ルーティン | 少なくとも1つの非開発ワークフローを安全に完了 |
| Phase 3：チーム機能 | 招待・権限・共有ビュー・組織課金 | 所有者の同意と権限に基づく共有を実現 |

### 5.1 初期対象外

- Agents Officeのコードを改変・再販売・埋め込みすること。
- 35体のAIを常時実行し続けること。
- 他人の実行状況をデフォルトで表示すること。
- 外部のすべてのAIツール（未接続のローカルClaude Code等）を自動的に監視すること。
- 本番環境への無承認デプロイ、mainへの無承認マージ、外部への無承認送信。
- ローカルブラウザの操作権限を自動的に引き継ぐこと。
- GitHub Enterprise Serverや任意のMCPサーバーへの無制限接続。

## 6. 成功指標（仮説）

| ID | 仮の目標 | 測定 |
|---|---|---|
| KPI-01 | 自分のRun状態を一覧・3Dの両方で正確に把握できる | 状態整合性テスト |
| KPI-02 | GitHubイベント受信からRun登録までp95で60秒以内 | Webhook受信とDB作成の時差 |
| KPI-03 | 対象の小規模IssueでDraft PR作成に到達する割合70%以上 | 成功run / 評価対象run |
| KPI-04 | 他利用者のデータ取得が全テストで拒否される | 越境認可テスト |
| KPI-05 | 承認なしの重要な外部操作0件 | 監査ログと統合試験 |
| KPI-06 | Runごとの費用見積もり・実行時間が可視化される | 計測欠損率 |

> 数値は初期検証の目標値であり、性能保証やSLAではない。正式値はPoC/ベータ試験後に決定する。

## 7. 事業・品質上の要求

1. **利用者間の機密保持**：ユーザー認証だけでなく、API、DB、ストレージ、検索、実行環境、GitHub App連携で所有者権限を確認する。
2. **最小権限**：GitHub Appは必要リポジトリだけにインストールし、書き込み権限は機能単位で最小化する。
3. **操作の追跡可能性**：Webhook、実行者、モデル/Agent版、ツール呼び出し、成果物、承認、エラーを追跡する。秘密値や全コードを平文ログへ出さない。
4. **再現性**：同一イベントの再配信でジョブが二重作成されず、途中失敗は制限された回数で再実行できる。
5. **費用統制**：ユーザー単位の同時実行・実行回数・トークン/時間上限を設ける。
6. **独自IP**：UI素材・デザイン・コードは独自作成または商用利用できるライセンスを確認した第三者素材のみ使用する。
7. **選択可能性**：エージェント実行部は交換可能にし、Claudeや別モデルを将来追加できるようにする。
8. **現実的なUX**：3Dは可視化レイヤーであり、遅い端末やWebGL非対応でも機能を失わせない。

## 8. 主要リスクと対策

| ID | リスク | 基本対応 |
|---|---|---|
| R-01 | Agentに社内の秘密や個人情報を読み取らせる | 接続スコープ/除外パス/データ送信規約/ログマスキング |
| R-02 | リポジトリ内の不正スクリプトがRunnerから外部流出 | エフェメラルコンテナ、非特権、ネットワークegress制限、最小IAM |
| R-03 | IssueやREADMEのプロンプトインジェクション | 不信頼入力として扱い、ツール呼出しをプログラムのポリシーで検証 |
| R-04 | 自動実行ループの暴走と費用急増 | 起動条件、再試行上限、同時実行数、予算、キルスイッチ |
| R-05 | PRレビューや外部送信の誤承認 | サーバー側で状態・所有者・承認対象ハッシュを検証 |
| R-06 | 3Dが実行状態より先に表示される | DBの確定状態を唯一の正とする。UIイベントは再取得可能にする |
| R-07 | OSSのライセンス違反 | Agents Office固有コード/アセットを利用しない。依存ライセンス台帳を管理 |
| R-08 | 個人ワークスペースに実装が偏り将来拡張しにくい | `workspace_id`境界を導入、チーム共有は明示的な将来拡張として設計 |

## 9. 決定済み事項と未決定事項

### 9.1 決定済み

- React + Vite + TypeScript、Three.js + React Three Fiberによる独自3D可視化。
- Hono + Node.js、AWS中心のクラウド構成。
- OpenAI Agents SDK（汎用エージェント）+ Codex SDK（開発エージェント）を初期候補に採用。
- Step Functions / SQS / ECS Fargateをオーケストレーション・実行レイヤーに採用。
- 初期サービスは個人開発者ごとの非公開ワークスペース。Organization共有モデルは必須にしない。
- Agents Officeの既存フレームワーク/ソースコード/アセットは利用しない。

### 9.2 未決定（実装前に確定する）

| ID | 論点 | 現時点の仮置き |

| O-01 | 料金体系 | ベータは利用量上限付き、課金方式は未決定 |
| O-02 | LLM/APIキーの負担 | サーバー管理キーから開始、BYOKはP2 |
| O-03 | 本番リージョン | AWS東京候補。データ所在要件によって再検討 |

| O-05 | リポジトリ/企業利用規約 | 接続前にユーザーの権限・会社の利用ポリシーを確認 |

## 10. 要求定義の受け入れ条件

- 主要利用者と可視範囲（自分専用）が認識一致している。
- MVPで可視化する「Run」が本サービス管理下の実行であると明確になっている。
- GitHub自動実行条件、承認範囲、停止条件、費用上限が合意されている。
- 現時点で対応しない機能が明示されている。
- 要件定義書のFR/NFR、および基本設計書の各機能と追跡可能である。

## 用語集

| 用語 | 意味 |
|---|---|
| User | アカウント所有者である開発者 |
| Workspace | 個人のタスク・Agent・Project・接続の集合とアクセス境界 |
| Project | Workspace内の開発案件・業務案件 |
| Agent | 役割と許可ツールを持つAIの論理担当。キャラと実行プロセスは1対1とは限らない |
| Run | 1つのイベント/指示から開始するワークフロー実行 |
| Step | Run内のタスク工程。個別Agentに割当可能 |
| Artifact | Draft PR・レポート・資料・メール下書き等の成果物 |
| HITL | Human-in-the-Loop。外部操作の前に人が確認・承認する仕組み |
| Source-available | コードは閲覧可能でも、利用・再配布に条件がある公開方式 |
