## 1. システム境界

### 1.1 論理境界

サービスは、サインイン、個人WorkspaceとProject、GitHub連携、イベント受信、Agentの実行管理、成果物・承認、3Dオフィス／2D一覧、監査・利用量を提供する。AIモデル、GitHub.com、各種外部SaaSは外部システムとする。

**可視化対象の限定**：MVPで見えるのは本サービスに登録・接続され、イベントを収集できるAgent Runだけ。利用者のPCにある未接続のClaude CodeやCodexを自動探知する機能はない。

### 1.2 データ境界・権限

- `User`：Cognitoで認証された利用者。
- `Workspace`：個人データの認可境界。MVPでは`owner_user_id`を一意に持つ。1ユーザーが複数Workspaceを持てる設計とするかは実装時に確定（初期は1つを推奨）。
- `Project`：Workspace内の案件。複数リポジトリを関連付けられる構造にするが初期UIはシンプルに保つ。
- `RepositoryBinding`：GitHub App installation/repository IDとWorkspace/Projectの正当な接続を表す。
- `Run`、`RunStep`、`Agent`、`Approval`、`Artifact`、`EventLog`：必ずWorkspaceに紐づける。
- ユーザーAはユーザーBのデータを取得・更新できない。DBフィルターだけでなく、サーバー側認可と必要な実行権限を組み合わせる。
- GitHubの共有リポジトリを複数利用者が登録した場合も、各Workspaceの実行情報は分離し、Webhookの振り分けは明示的に登録・検証した接続だけに行う。

### 1.3 認証と操作権限（MVP）

| 操作 | Workspace Owner | 他ユーザー | サービス運用者 |
|---|---|---|---|
| 自分のRunやProject閲覧 | 可 | 不可 | 原則不可 |
| Agent実行開始／停止 | 可 | 不可 | 例外時のみ監査付き |
| GitHub接続・解除 | 可（GitHub側権限が必要） | 不可 | 不可 |
| 承認・差し戻し | 可 | 不可 | 不可 |
| 実行履歴・費用閲覧 | 可 | 不可 | 集計のみを原則 |
| 他人のWorkspaceへの招待 | 未提供（P2） | 未提供 | 未提供 |

## 4. 承認・許可ポリシー

| 操作 | 初期ルール | 理由 |
|---|---|---|
| Issueや読み取り可能なRepoの解析 | 許可された範囲で自動 | 受動的操作 |
| リポジトリ内での作業ブランチ作成・コミット | ユーザーが許可したRepo・Runのみ | 差分追跡可能 |
| Draft PR作成 | Repo設定により自動化可能 | 人がレビューできる提出物 |
| mainへのマージ | **常に人間の操作** | 本番への無承認変更禁止 |
| GitHub Secrets・Branch Protection変更 | **原則禁止** | 高リスク変更 |
| 外部メール/Slack送信 | P1で明示承認後のみ | 誤送信予防 |
| 外部への文書公開 | P1で明示承認後のみ | 機密流出予防 |
| 本番クラウド設定・本番DB変更 | MVPでは禁止 | 影響範囲が大きい |

承認は「何を承認するか（対象ID/宛先/本文/差分）」「誰が承認できるか」「いつまで有効か」をサーバー側で固定する。AIのsystem promptに書くだけで制御したことにしない。

## 5. Run/Agent状態と操作ルール

### 5.1 Run状態

| 状態 | 意味 | 主な遷移先 |
|---|---|---|
| `queued` | 起動条件一致、受付済み | `planning`, `cancelled` |
| `planning` | 実装計画・権限確認 | `running`, `needs_input`, `failed` |
| `running` | AI/ツール実行中 | `validating`, `needs_input`, `failed`, `cancelled` |
| `validating` | テスト・レビュー | `pr_ready`, `running`, `failed` |
| `pr_ready` | Draft PR作成成功 | `waiting_review` |
| `waiting_review` | GitHubで人間のレビュー待ち | `revising`, `approved`, `cancelled` |
| `revising` | 差し戻しに対応 | `running`, `failed` |
| `needs_input` | 仕様不明・危険操作などの回答待ち | `planning`, `cancelled` |
| `approved` | レビュー承認を認識 | `completed`（マージは別操作） |
| `completed` | 対象Runの終了 | 終端 |
| `failed` | 自動復旧不能 | 終端／手動再起動で新Run |
| `cancelled` | 利用者が中断 | 終端 |

**注意**：このRun状態とキャラクターの表示状態は別ドメイン。UIの`idle`は紐づく実行がないこと、`working`は複数のRun状態を集約した表現である。`waiting_approval`はRunの承認待ちまたはApproval未処理に対応する。

### 5.2 冪等性・競合ルール

- Webhookイベントの一意性は`provider + delivery_id`を基本とし、DBのユニーク制約で二重起動を防ぐ。
- 同一Issueで同時に2件の開発Runを起動しない。既存Runがあれば更新キューへ登録するか拒否する。
- PRへのコメントが複数届いた場合はイベントを集約し、最新レビューcommit SHAを根拠に再修正する。
- レビュー待ちはDBで永続化する。長期間の人間待ちについてStep Functionsを稼働し続ける前提にせず、レビューイベントで**新しいワークフロー実行を再開**する。
- キューは少なくとも1回の配信を想定し、取り出し先も冪等にする。
- UIはサーバーの確定した`status_version`または連番イベントで表示を同期する。

### 7.1 3Dオフィス表現ルール

1. 実行状態はサーバーのRun/Step/Approvalから派生させる。キャラクターの勝手な演出によって「作業中」と誤認させない。
2. 1つのキャラクターは「論理Agent」を表現し、裏で同時に複数のRunnerが動いていてもUIは集約してよい。Agent数≠コンテナ数。
3. 重要な状態は色に加えラベル・アイコン・ツールチップで表示する。
4. 3D場面が描画できない場合に切り替え可能な2Dモードを提供する。
5. 3Dの独自アセットを利用し、Agents Officeの固有3Dモデル・素材・コードはコピーしない。
6. WebSocket/SSEが切れても、再接続時にGET APIで正しい状態を復元する。

## 9. 品質ゲート（リリース条件）

- **必須**：認証・越境認可E2Eテストが全合格。
- **必須**：Webhook署名検証、再配信の冪等性、キャンセル・予算停止テスト合格。
- **必須**：承認なしの外部送信・mainマージに到達しない。
- **必須**：3DなしでもRun詳細と承認が操作できる。
- **必須**：第三者ソース/3D素材の権利・ライセンス確認、SBOM。
- **必須**：秘密値/トークンの保護、CloudWatchログに不用意な情報がないこと。
- **検証目標**：初期のWebhook遅延/Run作成時間、3D描画性能、費用をテストで計測。
